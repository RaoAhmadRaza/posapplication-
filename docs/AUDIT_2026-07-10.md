**Flag — SECURITY DEFINER with NO permission gate:** `next_number`
(`supabase/migrations/20260613075616_stock_ops.sql:51-73`). Only checks `v_tenant is null`; no
`auth_has_permission` or `auth_has_branch` call. Any authenticated tenant user (any role) can call it
directly for any `number_series_type_enum`/branch and burn/skip document numbers (INVOICE,
STOCK_TRANSFER, STOCK_COUNT, etc.). Low severity (no data exposure, no financial-record forgery —
worst case is gap/skip in sequential numbering) but inconsistent with every other mutating RPC.

### (b) Highest-risk finding
`public.next_number(p_type, p_branch_id)` (`supabase/migrations/20260613075616_stock_ops.sql:51-73`)
is `SECURITY DEFINER`, granted to `authenticated`, and checks only `auth_tenant_id() IS NOT NULL` —
no `auth_has_permission` and no `auth_has_branch` call. Any authenticated user in a tenant (even one
with zero granted permissions) can call it directly with an arbitrary `branch_id` (not necessarily
their own) and `number_series_type_enum`, silently incrementing/creating that series' counter —
causing document-number gaps or cross-branch numbering pollution for INVOICE/STOCK_TRANSFER/
STOCK_COUNT/etc. Not a data-exposure or financial-forgery bug (it doesn't create real records, just
burns a sequence value), but it's the one gap in an otherwise consistently-gated RPC surface and
should get the same `auth_has_branch(p_branch_id)` check `ensure_default_warehouse` already has.
